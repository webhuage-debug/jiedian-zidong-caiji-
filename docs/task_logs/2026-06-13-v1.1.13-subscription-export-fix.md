## 问题根因

v1.1.12 的发布池导出会先读取 publish_subscription_pool，再 join 有效节点表，并在返回前调用 final_subscription_nodes。
final_subscription_nodes 会按地区白名单再次过滤。人工验收发布池中的 CF、unknown 或不在默认地区白名单内的节点，可能被二次过滤为空。
同时，旧逻辑依赖有效节点表 join，发布池里已有 uri 但有效节点表缺少对应记录时，也无法导出。

结果就是发布池有启用节点，但 /sub/<token> 生成的原始 Base64 订阅为空，转换订阅随后把空内容传给 Sub-Store。

## 修复说明

1. publish_pool_nodes 改为以 publish_subscription_pool.uri 为唯一发放来源。
2. 仍然只导出 publish_enabled=1 且 manual_status=publishable 的节点。
3. 如果有效节点表里存在对应记录且 manual_disabled=1，则不导出。
4. 不再对人工发布池做地区白名单二次过滤。
5. 不从 premium_subscription_pool 兜底。
6. 不从有效节点库兜底。
7. 转换订阅在调用 Sub-Store 前会检查原始内容是否为空；为空时返回“发布池没有可导出的节点”。
8. token 达到最大访问次数时返回明确错误：“订阅链接已达到最大访问次数，请重新领取。”
